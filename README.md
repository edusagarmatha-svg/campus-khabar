# Campus Kabar

Campus Kabar is a campus news and publishing platform: a public news portal plus a staff editorial console for news, articles, notices, announcements, multimedia, and an approval workflow.

## Architecture

```
Browser
  │
  │  one origin: the API serves the app, the API and the media
  ▼
Express 5
  ├── /          React 19 + Vite bundle, SPA fallback
  ├── /api/*     JWT access tokens (in memory) + rotating refresh cookie
  │              Zod validation, role checks, Knex
  ├── /uploads/* uploaded media, read-only, immutable cache
  │                  │
  │                  └── persistent volume (MEDIA_STORAGE_PATH)
  │                          media/<env>/<type>/<yyyy>/<mm>/<uuid>.<ext>
  │                          tmp/   in-flight uploads, never served
  └── MySQL 8
```

- The frontend never connects to MySQL directly.
- Access tokens are returned in JSON and kept in memory; refresh tokens are HttpOnly, Secure in production, rotated on every use, and stored only as SHA-256 hashes.
- Media bytes are uploaded to the API as multipart form data and stored on a persistent volume. There is no third-party media provider. The API identifies every uploaded file from its leading bytes and ignores the browser-supplied MIME type and filename extension.
- Media is streamed to a temporary file outside the served directory, then moved into place, so a reader never sees a partially written file and a rejected upload leaves nothing behind.
- Stored paths contain a UUID and never change, so `/uploads` responses are cached as immutable. `file_url` is stored relative, which keeps rows valid across domains and environments.
- `robots.txt` and `sitemap.xml` are generated by the API from published, non-deleted, non-expired content.
- The app and the API share one origin. This is load-bearing: the frontend calls `/api` relatively and the refresh cookie is same-site. Splitting them across two hosts requires an absolute API base URL, real CORS and a cross-site cookie strategy.

## Prerequisites

- Node.js 22.23.x (the project is tested on Node 22.23.4)
- MySQL 8
- A writable directory for media storage (a mounted volume in production)
- Docker, if you build the deployment image locally

## Local setup

### 1. Backend

```bash
cd backend
npm ci
cp .env.example .env
chmod 600 .env
```

Fill in `DB_*`, `JWT_ACCESS_SECRET` and `PUBLIC_SITE_URL`. `MEDIA_STORAGE_PATH` may be left empty locally: development falls back to `backend/var/storage`, which is gitignored. Generate a JWT secret with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Create the database and run migrations:

```bash
mysql -uroot -p -e "CREATE DATABASE campus_kabar CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci"
npm run migrate
npm run seed
npm run create-admin
npm run dev
```

The API listens on `http://localhost:4000` by default.

### 2. Frontend

```bash
cd frontend
npm ci
cp .env.example .env.local
npm run dev
```

Set `VITE_PUBLIC_SITE_URL` to the public origin used for canonical URLs and social metadata. The Vite dev server proxies `/api` to `http://localhost:4000`.

## Production configuration

At minimum, production must set:

- `NODE_ENV=production`
- `PUBLIC_SITE_URL=https://news.example.com` (HTTPS, no trailing slash)
- `CORS_ORIGIN=https://news.example.com`
- `TRUST_PROXY=true` or the exact proxy hop count when behind a load balancer
- `DB_SSL=true` when `DB_HOST` is not localhost, with `DB_SSL_CA` if the provider requires a private CA
- `JWT_ACCESS_SECRET` of at least 32 characters
- `COOKIE_SECURE=true`; production refuses to start if this is false
- `MEDIA_STORAGE_PATH` pointing at the mounted volume; the directory must be writable

The backend also refuses to start in production when a remote database is configured without TLS, when `PUBLIC_SITE_URL` is not HTTPS, when a rate-limit value is invalid, or when the media volume is missing or read-only. A `*.railway.internal` database host is exempt from the TLS requirement: that traffic never leaves Railway's per-project private network, and the managed database does not expose TLS there.

Never commit `.env` files. Keep the backend `.env` at mode `600`; production refuses to start if the file is group- or world-accessible.

### Deployment shape

The API serves everything from one origin: the built frontend, `/api/*`, the SEO
files, and uploaded media from the volume at `/uploads/*`. It applies the cache
headers itself — immutable for hashed assets and stored media, `no-cache` for
`index.html`. A reverse proxy is optional; where one is used, TLS terminates
there and `TRUST_PROXY` must be set so rate limiting sees real client IPs.

`FRONTEND_DIST_PATH` tells the API where the built bundle is. If that directory
is absent the API still serves `/api`, `robots.txt` and `sitemap.xml`, which is
what local API-only development and the test suite do.

Because uploaded media lives on a volume, the service runs as a **single
replica**: a volume cannot be attached to more than one instance. Scaling
horizontally later means moving media to object storage behind the same
`/uploads` paths.

### Railway

The repository ships a `Dockerfile` and `railway.json` for a single Railway
service plus a managed MySQL database.

1. Create the service from this repository. `railway.json` selects the
   Dockerfile builder and the `/api/health` healthcheck.
2. Add a **MySQL** database to the project.
3. Attach a **volume** to the service, mounted at `/data`.
4. Set the service variables:

   | Variable | Value |
   | --- | --- |
   | `NODE_ENV` | `production` |
   | `MEDIA_STORAGE_PATH` | `/data` |
   | `PUBLIC_SITE_URL` | the public HTTPS origin, no trailing slash |
   | `VITE_PUBLIC_SITE_URL` | the same origin (read at build time) |
   | `CORS_ORIGIN` | the same origin |
   | `TRUST_PROXY` | `true` |
   | `COOKIE_SECURE` | `true` |
   | `JWT_ACCESS_SECRET` | 32+ random characters |
   | `DB_HOST` `DB_PORT` `DB_USER` `DB_PASSWORD` `DB_NAME` | reference the MySQL service's variables |

   `PORT` is injected by Railway. `VITE_PUBLIC_SITE_URL` is inlined into the
   bundle during the build, so changing it requires a redeploy, not a restart.
5. Deploy. The container applies migrations and then starts the API.
6. Create the first Admin:

   ```bash
   railway run --service <service> npm run create-admin
   ```

### Migrating media from a previous provider

`backend/src/scripts/migrate-cloudinary-media.js` moves media that still points
at a remote provider onto the volume. It downloads each asset, re-validates it
through the normal storage path, repoints the `media` row at the local copy, and
rewrites the absolute URLs embedded in `posts.content` and
`post_revisions.content`. Media ids do not change, so the `post_media` and
`post_revision_media` link tables need no rewriting.

```bash
cd backend
npm run migrate-media -- --dry-run   # report what would move
npm run migrate-media                # perform it
```

The script is idempotent and safe to re-run: rows already on local storage are
skipped, and a failed download leaves its row untouched and is listed at the
end. Run it where both the database and the volume are reachable — on Railway,
`railway run --service <service> npm run migrate-media`.

## Admin operations

- Use `npm run create-admin` only for the first Admin. It is interactive and refuses to create a second Admin.
- Use `npm run reset-admin-password` to recover an existing Admin. It updates the password hash and revokes that account's active sessions.
- Follow [`docs/ADMIN_RECOVERY.md`](docs/ADMIN_RECOVERY.md) for the full recovery procedure.

## Verification

```bash
cd backend
npm test        # requires a dedicated campus_kabar_test database on port 3308
find src -name '*.js' -print0 | xargs -0 -n1 node --check

cd ../frontend
npm run lint
npm run build
```

The backend suite intentionally refuses to run against the normal development
database. It expects a `campus_kabar_test` database on port `3308`, which is
easiest to provide with a throwaway container:

```bash
docker run -d --name campus-kabar-test-mysql -p 127.0.0.1:3308:3306 \
  -e MYSQL_ROOT_PASSWORD=test-root-pw \
  -e MYSQL_DATABASE=campus_kabar_test \
  -e MYSQL_USER=campus_kabar \
  -e MYSQL_PASSWORD=test-password \
  mysql:8.0 --character-set-server=utf8mb4 --collation-server=utf8mb4_0900_ai_ci

cd backend
export NODE_ENV=test DB_PORT=3308 DB_NAME=campus_kabar_test \
       DB_USER=campus_kabar DB_PASSWORD=test-password
npx knex migrate:latest
npm test
```

Media tests write to a temporary directory, never to the configured storage
volume.

## SEO

- Canonical and Open Graph URLs use `VITE_PUBLIC_SITE_URL` on the frontend and `PUBLIC_SITE_URL` on the API.
- Media URLs are stored relative (`/uploads/...`); absolute URLs for social metadata are built from the configured public origin.
- `GET /robots.txt` points crawlers at `GET /sitemap.xml`.
- The sitemap excludes drafts, pending review, changes requested, unpublished, deleted, expired, and future-dated content.
- News posts emit `NewsArticle` JSON-LD; other posts emit `Article` JSON-LD.
- The public layout emits `Organization` and `WebSite` JSON-LD.
